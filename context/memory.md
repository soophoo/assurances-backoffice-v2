# Project Memory

> Project-local memory for agents. Read this at the start of a session; update it at the end.

## Decisions
- OpenAPI spec lives at `http://localhost:8080/api/v3/api-docs` — the base URL includes `/api` (`VITE_API_URL=http://localhost:8080/api`). The bare `/v3/api-docs` 404s. (2026-06-24)

## Patterns
- Forms use `@tanstack/react-form` + `zod`, with per-field `onBlur`/`onSubmit` validators and the shared `FormField` / `FormDialog` helpers. Canonical example: `src/components/users/AddUserModal.tsx`.
- ESLint is strict — two rules bite often: `@typescript-eslint/no-unnecessary-condition` (no `?? ''` / optional-chaining on values typed non-nullable; use `.charAt(0)` instead of `str[0] ?? ''`) and `import/consistent-type-specifier-style` (no inline `type` specifiers — use a separate `import type { X }` statement). Run `npx tsc --noEmit && npx eslint <files>` before declaring done.
- Routing is file-based (TanStack Router). After adding/removing a route file under `src/routes/`, run `npm run generate-routes` to regenerate `src/routeTree.gen.ts`.

  - `src/components/roles/PermissionMatrix.tsx` : composant contrôlé, matrice « domaine → actions » (puce pleine = accordée, pointillés = à accorder), filtre, dépliage « Accorder… », légende. Réutilisé par l'édition d'un rôle **et** la création.
  - `src/lib/permission-labels.ts` : libellés + descriptions FR des permissions (`partner:read` → « Partenaires — Consulter » / « Consulter les partenaires distributeurs. »). Toute nouvelle ressource backend doit y être ajoutée, sinon repli sur le nom technique capitalisé.
  - `/users` : clic sur une ligne → `AdminDetailDrawer` (Sheet droite) = rôle + `RolePermissionsEditor` (POST/DELETE `/roles/{roleId}/permissions/{permissionId}`).
  - `/roles` : clic sur une ligne → `RoleDetailDrawer` (Sheet droite) = renommage/description (`PUT /roles/{id}`, service `updateRole`) + même éditeur ; « Créer un rôle » → `CreateRoleDrawer` (Sheet droite) avec `AddRoleForm` réécrit (Select shadcn pour hériter d'un rôle modèle + matrice ; `TemplateSelector`/`PermissionsAutocomplete` supprimés). La page garde l'**id** du rôle sélectionné et le relit dans le cache pour refléter les permissions rafraîchies.
  - `/permissions` : colonne « Ce que ça autorise » ; « Ajouter une permission » et clic sur une ligne ouvrent le même `PermissionDrawer` (Sheet droite) — création `POST /permissions`, renommage technique `PUT /permissions/{id}` (services `createPermission`/`updatePermission`), nom validé `^[a-z][a-z0-9]*(:[a-z][a-z0-9]*)?$`, et suppression `DELETE /permissions/{id}` (service `deletePermission`) derrière un `ConfirmDialog` qui liste les rôles porteurs. Côté backend c'est un **soft delete** avec `@SQLRestriction("deleted_at IS NULL")` sur `Permission` : la permission disparaît du catalogue et de `role.getPermissions()`, donc de `User.getAuthorities()` — l'accès est perdu immédiatement pour tous les comptes du rôle, sans endpoint de restauration (les lignes `role_permissions` restent orphelines en base). Un champ de recherche sur `/permissions` charge tout le catalogue (size 200) et masque la pagination tant qu'il est rempli. L'**intitulé affiché** et la description sont des champs saisis à la main, seulement *proposés* d'après le nom technique. Comme `PermissionResponse` ne porte que `name`, ces libellés sont stockés en `localStorage` (`nsia:permission-labels`, helpers `permissionLabelOverride`/`setPermissionLabelOverride`/`clearPermissionLabelOverride`) : ils ne sont donc pas partagés entre postes — il faudrait une colonne `label`/`description` côté backend pour ça.
  - Gotcha backend : `POST /roles/{roleId}/permissions/{permissionId}` n'est **pas** idempotent (double lien) — n'envoyer que des permissions non accordées. Les mutations invalident `roles` **et** `roles-all` (clé lue par `usePermissions`). NOT verified live in the browser yet.
